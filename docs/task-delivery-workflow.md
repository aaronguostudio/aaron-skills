# From a task to a usable delivery

Aaron Skills describes **Understand → Build → Verify → Demonstrate → Deliver**.
The same method can serve a feature, application, deck, report, document or
reusable template. These are capabilities to combine, revisit or omit as the
task needs; they are not mandatory phases or a required set of files.

## Capability map

| Need | Capability / invocation ID | Useful result for the next receiver |
| --- | --- | --- |
| Understand the intended outcome and consequential choices | Shape / `feature-blueprint` | A clear interpretation, decision, design, workflow, model or execution brief |
| Carry agreed intent into actual work using the team's existing methods | Build / `build-delivery` | A usable artifact with applicable design, validation, compatibility and handoff requirements addressed |
| Establish what the actual result supports | Verify / `verify-delivery` | Evidence, scoped repairs/rechecks and material remaining limits |
| Explain an applicable experience | Capture / `demo-capture`, Film / `walkthrough-video` | An authorized, checked recording or guided video when useful |
| Make the result usable by its receiver | Deliver / `deliver-work` | Actual stakeholder communication, release notes or handoff with access and next action |
| Package a copyable screenshot update when helpful | Share / `paste-ready-update` | A local review/paste page using the existing Demo runtime |

The v1.0.0 standard installation includes all seven skills. Capture/Film/Share
retain their existing runtime and invocation IDs. Instruction availability does
not establish universal output quality, integration with third-party frameworks
or a successful joint behavioral trial of the whole method.

## Carry meaning and evidence, not a universal packet

Keep enough continuity for the next action: who needs what and why, settled
decisions, constraints/preferences, the actual artifact/version, observable
success, relevant evidence and open owner choices. Use the current conversation,
ticket, source files or other useful artifact; no shared schema or export format
is required. No skill is a prerequisite for another.

Build operates inside the chosen engineering or authoring workflow, reusing its
plans, design system, tests and review/release rules. Its delivery expectations
belong in that work rather than a second management process. No named framework
is required and no framework compatibility is implied without a real trial.

Build retains ongoing checking. A separate Verify pass can reassess the actual
result from the receiver's task; it may return a scoped defect to Build or a
material unresolved decision to the understanding work. Use changed evidence to
revisit the relevant part, rather than restarting every task from the beginning.

An existing satisfactory recording can be reused. A document or backend change
may need no video. Demonstration does not replace verification, and communication
does not replace handing over the actual files or working entry point.

## Examples of composition

**Application feature:** Shape carries the reason for a shared queue and its
accepted behavior. Build implements it in the existing project. Verify checks
URL restoration and authoritative state. Capture/Film may demonstrate the flow
when requested. Deliver prepares the test/release update and relevant adoption
or release handoff, accurately naming its availability. Share may package a
copyable update. None of these steps itself authorizes deployment or sending.

**Report or deck:** Use the supplied purpose, audience, sources and reference
style directly when clear. Build produces the requested editable/export files.
Verify checks argument, figures, completeness and rendered layout. Deliver
prepares the actual files and audience-appropriate note, with the decision or use
needed from the reader. A recording and software release notes may add no value.

**Reusable template:** Build creates/refines the template and its intended reuse.
Verify exercises representative inputs and repeat runs, then inspects generated
outputs. Deliver supplies the template/source, input instructions and useful
examples or limits for the next user. Repairing only one generated sample does
not complete the reusable task.

## Finish at the right level of truth

Distinguish prepared, implemented, verified, deployed/enabled, sent and accepted.
Carry the actual scope and important limits into every audience's communication.
Follow authorized destinations and project release policies; a ready draft is
different from a sent message, and passing local checks is different from a
production release. Report the state actually reached and the next material
action without claiming customer acceptance from silence.
