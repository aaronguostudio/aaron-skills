# Optional portable packet

Read this only after choosing a structured full-case handoff. Prose, native
Canvas designs, existing project artifacts and lightweight changes do not need
this format, its fields, a JSON file or the checker. An explicit format choice
adds these constraints; ordinary use of Shape does not.

For a handoff using this format, `blueprint.json` owns the structured fields. Markdown and Mermaid are review views,
generated by `scripts/blueprint.py render`. Keep source files alongside it so
reviewers can inspect the excerpt's context. The renderer uses only the JSON;
it does not dereference locations, open source paths, call a service or run code.

Fields required **only by this optional complete-case format**:

| Field | Content |
| --- | --- |
| `schema`, `id`, `title`, `revision` | Schema `1`, stable ID, name, nonempty revision |
| `provenance` | `fictional` or `project`; fictional requires an explicit notice |
| `notice`, `outcome`, `scope`, `excluded`, `limits` | Strings; the last three are lists of strings |
| `sources` | `id`, `title`, `date`, `location`, `authority`, `excerpt` |
| `questions` | `id`, `round`, `question`, `why`, `options`, `recommendation`, `status`, `answer`, `blocking`, `owner`, `next`, `sources`, `decisions` |
| `decisions` | `id`, `text`, `sources` (evidence IDs) |
| `rules` | `id`, `text`, `decisions` |
| `states` | `id`, `label` (IDs are also legal Mermaid identifiers) |
| `transitions` | `id`, `from`, `to`, `action`, `actor`, `rules` |
| `entities` | `id`, `fields`: `{name, type, key}`; key is `PK`, `FK`, or empty |
| `relationships` | `from`, `to`, `label`, `cardinality`: `one-many` or `one-one` |
| `acceptance` | `id`, `given`, `when`, `then`, `verify`, `rules` |
| `slices` | `id`, `title`, `outcome`, `acceptance`, `dependsOn`, `notes` |

All collections contain at least one entry except `questions` and
`relationships`. IDs are unique across collections, start with a letter and use
letters, numbers or underscores only. Nonempty strings are required unless
explicitly allowed below. Empty/whitespace values fail. Unknown fields fail,
so misspelled contract keys cannot silently lose their meaning.

Question status is `open`, `resolved` or `deferred`. `round` is a positive integer;
`blocking` is a Boolean. Open/deferred entries may have an empty `answer` and
`decisions`, but need an `owner` and a concrete `next` action. Resolved questions
need answer text and decision IDs. Options have at least two strings. Every
question and decision points to evidence; every rule to a decision; every rule
has at least one acceptance scenario. Every acceptance scenario belongs to a
slice; slice dependencies must be acyclic. A source reference and nonempty
answer do not establish that an authorized human confirmed it.

`validate --ready` additionally rejects blocking open/deferred questions. It
does not approve the feature, authorize a build, evaluate semantic consistency,
detect every secret, or certify any platform. Keep this format opt-in: for a
tiny request, a concise prose handoff may be more useful.

`render --out` creates a previously nonexistent directory containing
`handoff.md`, `workflow.mmd` and `data-model.mmd`. It escapes diagram labels and
fences untrusted source excerpts in Markdown. Rendering never changes its input.
Prototype state, logins and database writes must remain visibly simulated until
implemented and independently verified.


The checker uses Python 3.11+ and the standard library. These commands do not
call a model, access a service, read linked sources or register a skill:

```sh
python /path/to/feature-blueprint/scripts/blueprint.py validate /path/to/blueprint.json --ready
python /path/to/feature-blueprint/scripts/blueprint.py render /path/to/blueprint.json --out /path/to/new-review-packet
```

Rendering creates a new directory. Inspect outputs before sharing; it does not
redact sensitive material. Keep raw project material and run evidence outside
public checkouts. Readiness describes declared blockers, not user acceptance.
