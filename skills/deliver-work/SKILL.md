# Deliver

Help the next receiver understand the result, access the work and take the right
next action. Prepare the actual message, release notes or handoff within scope;
a communication plan alone is not the delivery. Use the requested channel and
format, scaling the work to the task. A concise message may be sufficient. The
core has no runtime, connector or other skill dependency.

**Start with the receiver and their next action.** Use the brief, existing
decisions, actual artifacts and verification evidence to identify who needs what:
awareness, a decision, a trial, adoption, continued implementation or operation.
Preserve the user's audience, language, tone, timing and destination when given.
Resolve accessible facts from the project. Ask only for missing information that
changes the communication or blocks an authorized delivery; don't repeat settled
questions. If a destination is unknown, useful draft preparation can continue.

**Keep the result and its status truthful.** Carry the purpose and meaningful
before/after behavior into words the receiver uses. Separate what is proposed,
implemented, verified in a named environment, deployed, available to a particular
audience and accepted by them. Use the relevant version and evidence, including
material limits from Verify or other checks. A working demo does not establish
production availability, and a sent message does not establish acceptance.
Do not invent benefits, metrics, dates, owner commitments or a sender signature.

**Choose the expression and prepare it.** Follow the supplied channel; otherwise
recommend or use a suitable draft form based on the receiver's task and the
existing working context. Produce the actual content, not just an outline or an
offer to write it. Use only the outputs needed. An internal update, customer note,
durable release note and operational handoff can share facts while needing
different detail; keep their status and promises consistent.

Read only the applicable references:

- [Stakeholder messages](references/messages.md): meaningful changes, useful
  next actions, audience-specific wording and ready-to-use communication.
- [Channels and media](references/channels-media.md): chat, email, documents,
  screenshots, video, attachment access and optional Share packaging.
- [Release notes](references/release-notes.md): user-facing change explanation,
  applicability, action and honest release status.
- [Release and operational handoff](references/release-handoff.md): concrete
  release preparation, provenance, dependencies, operations and delivery checks.

**Use media to make something clearer.** Select existing checked screenshots or
video when they explain where to act, how a flow works or what changed. Inspect
them, ensure they match the delivered version and write text that remains useful
without playback. A short text update or backend change may need no media.
Reuse suitable assets. Request or create new capture/narration only within the
task's scope; preparation of a message is not automatic recording authority.

Share (`paste-ready-update`) is an optional way to package copyable text with
screenshots and video when installed. Capture and Film are optional ways to
create an authorized demonstration. Use their real capabilities and constraints;
do not implement a parallel page/video renderer or require HTML for every message.
When a tool is unavailable, deliver a useful supported form and identify the
missing capability rather than claiming it was used.

**Make the work usable from the receiver's context.** Supply the requested
artifact/version, required attachments and a sensible entry point. Check that
the message's links, file names, screenshots and actions refer to the actual
delivery. Local authoring paths are not external access links. Test recipient
access when the tools and authority allow it; otherwise disclose the access
limit and prepare the necessary transfer without inventing a public URL or
changing sharing permissions on your own.

Adapt the explanation to the medium: a report may need its sources and editable
file, a deck may need presenter notes, an app may need its environment and access,
and a reusable template may need input instructions. Preserve material issues,
open owner decisions and useful recovery information. Do not require a large
handoff packet where an existing file and a brief note will do.

When the next use includes rerunning checks or regenerating output, include the
necessary source, scripts and inputs. Replay promised commands from the delivered
package; the [channel reference](references/channels-media.md) covers this boundary.

**Distinguish preparation from external action.** A prepared note, release plan
or handoff does not authorize sending, uploading, merging, publishing, deploying
or changing access. For an explicitly authorized action, use the supplied target,
identity and scope with the appropriate available tools. Do not ask again for
permission already given; prepare the concrete result before any still-required
approval. Follow project release/provenance rules and the relevant tool workflow.
If the action's result is uncertain, inspect its state before retrying to avoid
duplicate messages or releases.

**Close with the actual outcome.** For a draft, identify the prepared content and
any remaining decision or attachment requirement. After an authorized delivery,
verify what was sent, attached or published to the intended destination; retain
useful version/link/status evidence and state any untested recipient access.
Keep prepared, sent, released and accepted distinct. Capture an explicit reply
or requested next action without interpreting silence as approval or creating
an unsolicited reminder/monitor. If feedback changes the substance, return to
the relevant understanding/build/check work and revise dependent communications.

Use only task-relevant authorized sources. Keep private material and raw media,
execution logs and personal configuration outside public source. Judge delivery
by whether the receiver can understand, access and act on the result, rather
than by message length, media count or a claim that everything is complete.
