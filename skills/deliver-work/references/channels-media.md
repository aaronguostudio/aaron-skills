# Channels and media

Read when choosing a communication form or preparing supporting files. Honor
the requested destination and existing thread. Use available channel tools and
their current instructions for actual delivery; do not assume a connector exists.

## Fit the channel to the next action

Use these as judgment aids, not required modes:

| Form | Useful when | Prepare |
| --- | --- | --- |
| Teams or another chat | A focused update, quick question or action in an existing conversation | Short body, relevant link, selected image/clip if helpful |
| Email | Specific recipients need context, a decision or a formal handoff | Subject, body, necessary links/attachments and supplied signature |
| Release notes | People need a durable account of a version's applicable changes | Reader-facing changes, availability, required action and material limits |
| Document or project handoff | Someone must continue, present or operate the work | Actual artifact/source, entry point, dependencies and next action |

One task can justify more than one form, such as release notes plus a short
announcement linking to them. Don't generate every form by default. If the task
only specifies preparation, choosing a draft form does not select an external
recipient or grant authority to send it.

## Decide whether media earns its place

Prefer a screenshot for a particular control, layout or resulting state. Prefer
a video when sequence, interaction or timing changes understanding. Use text or
a diagram when that explains the result more clearly. Reuse existing checked
media that matches the delivered version; record or render something new only
when the task authorizes it. No automatic video or narration is required.

Inspect every selected screenshot and relevant video segment. Ensure captions,
visible numbers, environment and roles support the message. Preserve originals;
crop, annotate or redact copies when appropriate and check those copies too.
Keep client data and private account details within their permitted audience.
Do not expose private files by uploading to an unrequested public host.

Give the receiver an understandable label, useful viewing context and sufficient
text without playback. For a long existing video, point to relevant sections if
available rather than requiring the receiver to watch it all.

## Package and check the actual delivery

Use Share (`paste-ready-update`) when a copyable screenshot/update page helps and
its runtime is available. Follow that skill's page/media instructions; keep
runtime ownership there. Its local HTML page is a review/paste artifact, not an
external sharing URL. Videos require the appropriate attachment or accessible
hosting step; text copying alone does not deliver the video.

For plain chat/email, prepare the actual body and files directly. Inspect the
channel's rendered draft when accessible: text, lists, links, images and attachments
can differ from the authoring view. Avoid relying on unsupported formatting.

Check attachment names and versions, relative asset dependencies, link access
and any required recipient sign-in. Sender access is not proof of recipient
access. If that access cannot be tested, say what remains to be checked. Don't
invent file-size limits or provider behavior; inspect the current tool/service
when a constraint matters.

## Check promised reuse from the delivered files

If the handoff offers a run, render or recalculation command, copy only the
recipient package to a fresh directory and replay the documented command unchanged
with its declared dependencies. Check the resulting content, not just exit status.
The source checkout, author-only fixtures, absolute asset paths and local helper
scripts are unavailable unless actually included or supplied through an agreed
access route. Preserve supporting inputs needed by the original checks; do not
weaken an assertion or substitute an easier example to obtain a pass.
If required historical evidence is missing, keep that claim unverified. A newly
recorded baseline starts new evidence; it cannot replace the missing reference.

Repair the package or command when that reuse is required. If it cannot be
verified, name the affected operation and practical limit in the handoff. Do not
promise reproducibility from a successful authoring run. This check is unnecessary
for a plain message or a reading-only file handoff that promises no rerun.
