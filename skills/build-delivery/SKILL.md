# Build

Carry user intent into finished work: suited to its audience, checked in use and
ready for its next receiver. Produce and improve the actual deliverable within
the authorized scope. A plan or quality checklist alone does not finish a build.
Build supplies delivery requirements within the user's engineering or authoring
system. That system owns implementation methods, planning, review and release.
Use the host's available tools; the skill has no runtime dependency. Scale the
work to the change, without mandatory phases, files or approval checkpoints.

**Continue from the understanding already available.** Read the relevant brief,
accepted design, workflow, conceptual model, examples and project conventions.
An existing Shape handoff is useful input, not a required format or prerequisite.
Carry forward who needs to do what, the intended result, settled constraints,
preferences and observable success. Preserve the reasons behind consequential
choices. Keep proposals and unanswered questions distinct from decisions; neither
a polished design nor a copied ticket promotes them into requirements.

Resolve accessible implementation facts from the project. Ask about a missing
owner decision only when it materially changes the result. Continue independent
reversible work while it is pending; an explicit assumption can support a
prototype but does not settle policy. If implementation evidence changes the
meaning or feasibility of the agreed result, explain the consequence and revisit
that choice rather than quietly substituting a different product.

**Work inside the existing system.** Inspect the applicable project instructions,
chosen skills/workflow, nearby implementation, design references, test commands
and release rules before choosing an approach. Reuse their plans, tasks and
review records; add delivery expectations there when useful. Keep the project's
test-first, review or branching practices rather than starting a competing plan.
Do not install a framework, rewrite project rules or replace a working toolchain
to satisfy this skill. No named framework or extra skill is required, and reading
its name is not evidence of integration.

Use the accepted design system, components, templates and assets. If there is no
documented system, look for consistent patterns in the actual product. Where
direction is missing, establish only the design choices needed for this task;
a representative slice can make them reviewable. A new product-wide design
system is a separate scope choice. Do not replace an accepted design for stylistic
preference or restart settled discovery. If a necessary tool is unavailable,
state the affected capability and use a suitable fallback only when it still
serves the requested medium and purpose.

**Close the relevant delivery gaps.** Connect the brief's success examples to
observable behavior and practical checks. For substantial application work,
resolve the design basis, meaningful navigation/state, input validation and
access boundaries, test coverage, compatibility and rollout needs. Use the web
reference for the applicable decisions. Follow existing requirements; fill gaps
in proportion to the change instead of treating every consideration as a new
feature or universal gate. A label edit should remain a label edit. Reuse existing
acceptance notes; a separate quality matrix is unnecessary. Explain a material
tradeoff, and keep an unresolved owner choice distinct from a technical default.

For software additions, connect new modules to the project's existing discovery,
registration and verification mechanisms where applicable. Check that new code
and tests are reachable and that relevant CI checks remain selected when a later
change touches only the new module. A broad current diff that runs everything
does not prove that coverage. Extend the owning rules narrowly; do not introduce
a registry or CI system where the project has none.

For data-backed work, preserve business meaning across live, mock and fallback
adapters. Check associations against the complete business identity and reconcile
amounts and totals within the same scope. Use shared acceptance examples and
independent expected results at the boundaries that could diverge; realistic
screens and passing mock tests alone do not establish real-adapter correctness.

Read only the references applicable to the current work:

- [Websites and applications](references/web.md): design reuse, navigation,
  validation, testing and registration within the existing process, compatibility
  and rollout.
- [Presentations](references/presentations.md): audience, argument, visual
  expression, editable delivery and inspection of the rendered deck.
- [Documents](references/documents.md): reader action, evidence, editing and
  inspection in the requested reading or export format.
- [Templates and generators](references/templates-automation.md): subsequent
  inputs, output replacement or version retention, and a usable repeat-run path.

**Express the user's taste in the artifact.** Use supplied examples and existing
work to infer specific choices about density, hierarchy, tone, imagery and
interaction. Treat a new inference as provisional; never turn one preference
into a universal style. Create a representative working slice, slide or section
early when it can expose a costly misunderstanding. Use realistic content and
the actual constraints of the medium. Reuse an accepted sample rather than
adding a preview ritual. Keep completing the deliverable when direction is
clear; silence is not approval for an unresolved choice.

**Check and revise the work where it will be used.** Exercise the core task,
relevant failure/recovery paths and observable success examples. Inspect the
actual rendered or running result, not just source or a successful build command.
Choose checks proportional to the change; use the project's required tests and
specialist verification when relevant. Fix observed gaps and recheck the affected
behavior. Keep simulated data, inactive controls and untested integrations
visible as such. A screenshot cannot prove persistence; a file that opens cannot
prove its argument or calculations are correct.

A separate Verify pass can reassess the actual deliverable and its evidence for
the next use. It is optional and does not defer or replace these ongoing checks.

Carry feedback into every affected part of the actual deliverable, including
interaction, content, data meaning, examples and handoff. Check that those parts
still agree. Preserve source material and unrelated work. Richness comes from
serving the task with complete, coherent details; avoid adding features, visual
effects or documents merely to make the output appear substantial.

**Finish for the next receiver.** Deliver in the requested location and format,
with working entry points, required assets and editable source when that is part
of the request. Check that links and files make sense from the receiver's access
context; a notice linking to a file is not a replacement for that file. Adapt the
handoff to what the receiver needs to do: use the result, assess a decision,
continue implementation or operate it. Reuse existing notes or project artifacts
instead of requiring a separate packet. State what changed, the checks actually
performed and any material limits or remaining owner choices.

Keep proposed, implemented, verified, released and user-accepted states distinct.
Preparation does not establish recipient access or customer acceptance. Follow
existing task authorization for external delivery and release; creating a
deliverable adds no permission to send, publish, deploy or purchase services.
Keep private sources, personal configuration and raw execution evidence outside
public source. Judge success by the receiver's ability to complete the intended
next action without reconstructing critical intent.
